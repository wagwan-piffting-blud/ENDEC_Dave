# loqng

The Loquendo TTS 6.9 engine, running as native Rust. **Byte-identical to the ARM original pulled off the DIGITAL ENDEC**, no interpreter, no emulator, no ARM.

```sh
loqspeak "Hello there." -o hello.wav # "59 characters -> 4.11 s of audio in 0.05 s (85x real time)"
```

## Status: mostly complete, SAPI support pending

The whole engine - `LoqTTS6.so`, `LoqEnglish6.9.so`, `loqmsx.so` and `LoqAudioFile.so`, **180,590 ARM instructions** - is translated to Rust, one statement per instruction, and runs on a small runtime (`loqng-xrt`) plus a hand-written host for the 94 libc and pthread calls it makes.

| gate | what it proves | result |
|---|---|---|
| `xtask engcorpus` | the library speaks the corpus | **37/37 byte-identical**, 171 s of audio |
| `tools/packcheck.py` | the *shipped binary*, through its built-in voice tree | **37/37**, and identical to the same tree on disk |
| `xtask engprobe` | one translated module against the ARM function | 102 corpus phrases + 50,000 random windows |
| `xtask refpcm` | the ported codec against the ARM decoder | 200 frames, 64,000 samples |
| `cargo test` | data formats, codec internals, stage types | 167 pass |

There is **no tolerance anywhere**, including prosody floats. A capture either matches to the byte, or it is a bug.

## `loqdave` - the deliverable

One executable, 35 MB, with the voice tree baked in. Nothing beside it, no install step.

```sh
loqdave "Hello there." -o hello.wav
loqdave --file script.txt -o out.wav       # `-` is standard input
loqdave --serve < requests.tsv             # one request per line, warm
```

`--serve` is the mode for a service: the voice loads once, then a short phrase costs about 6 ms instead of 200.

## Platforms

```text
loqdave-windows-amd64.exe    x86_64-pc-windows-msvc          for Windows 10/11 64-bit
loqdave-linux-amd64          x86_64-unknown-linux-musl       for x86_64 Linux (aka most desktop/server distros)
loqdave-linux-arm64          aarch64-unknown-linux-musl      for Pi 3/4/5, Zero 2 W
loqdave-linux-armv7          armv7-unknown-linux-musleabihf  for Pi 2/3/4, 32-bit
loqdave-linux-armv6          arm-unknown-linux-musleabihf    for Pi 1, Zero / Zero W
loqdave-macos-universal      aarch64 + x86_64-apple-darwin   for Apple Silicon and Intel Macs, one file
```

`build_targets.ps1` builds all five from Windows with **no cross toolchain** - the Linux targets are static musl, linked by Rust's own bundled `rust-lld`. Copy one anywhere and run it.

macOS has to be linked on a Mac. `build_targets.ps1 -Mac user@host:/path/to/this/checkout` runs `build_macos.sh` there over ssh, which builds both slices, `lipo`s them into one binary and runs the corpus through each - the Intel slice under Rosetta. It is then signed with a Developer ID (hardened runtime) and notarized, so Gatekeeper opens it without a warning; a bare Mach-O cannot be stapled, so the first run checks the ticket online. The login keychain is locked over ssh, so the script asks for the Mac password to sign. The universal file is 74 MB because each slice carries its own copy of the voice tree. On an M4, a 1,040-character paragraph runs at 136x real time native and 109x under Rosetta.

The 32-bit ARM targets use a different guest-memory implementation: a 64-bit host reserves the whole 4 GB guest space so a load is `base + a`, which a 32-bit host cannot do, so those fall back to a page table at roughly half the throughput. The audio is byte-identical either way, and `tools/packcheck.py --run` checks every target under qemu.

## Speed

7900X, warm engine, one voice load:

```text
  size          chars   audio s    best ms   x real time
  one word          4     1.116       6.27       178
  short            67     4.480      40.28       111
  medium          306    17.864     157.34       114
  long           1040    60.088     541.22       111
  huge          16057   920.886   11183.18        82
```

Fixed cost per utterance is below zero by least squares - a short phrase is *cheaper* per second of audio than a long one, because a long one has more distinct units to select. There is no length limit; the binding constraint is memory, since the sink holds the audio (921 s is 29 MB).

The first working version ran at 14.4x. What made it 5.7x faster, in order: holding the whole 32-bit guest address space as one reserved 4 GB window so a guest load is `base + a` rather than a page-table walk; holding the condition flags in a local per function so the compiler can delete the ones nothing reads; and a profile-guided build. `xtask engprof` is the profiler that found the first one.

## Layout

```text
crates/loqspeak/       THE BINARY: text in, WAV out, one file
crates/loqng/          the runtime host: heap, VFS, libc, cooperative threads
crates/loqng-eng/      GENERATED by tools/engxlate.py - the whole engine
crates/loqng-xrt/      the translation runtime: Cpu, Flags, FPA11; mem.rs holds the two guest-memory implementations
crates/loqng-voice/    GENERATED by build.rs - the voice tree, include_bytes!
crates/loqng-data/     .vde .lde .lex .sde .phd .atm .bin parsers
crates/loqng-codec/    the loqmsx replacement, bit-exact
crates/loqng-oracle/   wraps loqrs; the ONLY crate allowed to
xtask/                 capture, replay, engcorpus, engbench, engprof, ...
```

The workspace has **no external dependencies**. No serde, no clap, no anyhow - not even for the 4 GB reservation, whose two system calls are declared by hand in `loqng-xrt`.

## Building

```sh
cargo build --release -p loqspeak      # ~75 s if the engine is cached
```

The voice tree is taken from `$LOQ_LIB` and `$LOQ_DATA`, defaulting to the sibling `engine/{lib,data}`. A build that finds no tree still compiles; `loqspeak` then needs `--lib` and `--data`.

To retranslate the engine after changing the translator:

```sh
python tools/engxlate.py crates/loqng-eng/src    # 3.4 s
cargo build --release -p loqspeak -p xtask       # 75 s
target\release\xtask.exe engcorpus               # the gate
```

## How it was done

Not by reverse engineering the engine's meaning. `tools/fonsurvey.py` counted the instruction *forms* in the hardest module and found 70 of them, which made mechanical translation obviously cheaper than understanding - and, unlike understanding, verifiable to the byte. `tools/textcover.py` then showed that seeding reachability from exported symbols, relocation targets, GOT-computed addresses and every `push {...,lr}` prologue reaches 96.7% of `.text`, which turned "reverse engineer 206 KB of ARM" into "translate it and implement 94 libc calls".
